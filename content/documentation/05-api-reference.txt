# 1. Architecture at a glance
This is a Shopify **React Router (Remix-style)** app. Every file under `app/routes/` is a route. Most route files are a one-line re-export - `export { loader, action } from "../domain/.../x.server.js"` - so the real logic lives in `app/domain/**`.
- `loader` handles `GET` requests.
- `action` handles `POST` (and other write) requests.
- Routing is file-based, driven by `app/routes.js`.
**Why some endpoints have two paths.** A few storefront endpoints have two route files that serve the exact same handler, for example `api.quote.jsx` and `apps.$proxySubpath.api.quote.jsx`. In production, Shopify's App Proxy strips the `/apps/{subpath}` prefix before forwarding a request to the app, so the real path (`/api/quote`) is what the app sees. Under `shopify app dev`, the CLI forwards the request without stripping that prefix, so without the alias route it would 404. `$proxySubpath` is a wildcard, not a fixed value, so the alias keeps working no matter what `[app_proxy].subpath` is set to. Behavior is identical either way - this is mentioned once here instead of repeating it on every endpoint below.

	`shopify.app.toml` declares `[webhooks] api_version = "2026-07"`, while the app code sets `ApiVersion.October25` ("2025-10"). These control different things (webhook payload version vs. Admin API client version), but the mismatch is worth reconciling with whoever owns the Partner app config.
</callout>
## 2.1 Shopify admin session
Call: `authenticate.admin(request)`.
This is the SDK's standard guard for anything running inside the embedded Shopify admin. It validates the request's session token (a JWT) against the stored session, or triggers the OAuth/token-exchange flow if there isn't one yet. On failure it throws its own `Response` - a redirect to OAuth for a page load, or a 401/403 for a fetch call - before any route code runs. No route in this app adds custom handling on top of that.
## 2.2 App Proxy signature
Call: `authenticate.public.appProxy(request)`.
Verifies the HMAC `signature` query parameter that Shopify attaches when it forwards a storefront request through the App Proxy, and returns a verified `session.shop`. The shop domain always comes from that verification - never from a client-supplied field. If `session.shop` can't be resolved, the route returns:
```json
{ "error": "Shop not installed" }
```
with HTTP status `401`.
## 2.3 Per-quote PDF token
Used only by `GET /api/quote/:id/pdf?token=<hex>` - no Shopify auth is involved at all.
`verifyQuoteToken(id, token)` (`app/domain/pdf/pdfToken.server.js`) recomputes the expected token and compares it to the one supplied:
```javascript
signQuoteToken(quoteId) =
  crypto.createHmac("sha256", secret).update(String(quoteId)).digest("hex")
```
The comparison uses `crypto.timingSafeEqual`, a deliberate choice to prevent timing attacks. The secret comes from `process.env.ENCRYPTION_KEY`, falling back to `process.env.SHOPIFY_API_SECRET`. In production, if neither is set the app refuses to start (`[SECURITY]` error); outside production it silently falls back to the hardcoded string "dev-insecure-pdf-token-secret".
<callout icon="⚠️" color="yellow_bg">
	This token never expires. It's a deterministic HMAC of the quote id with no timestamp or nonce, so it stays valid indefinitely as long as the secret doesn't change. Anyone who obtains the emailed link can reuse it at any time. Worth knowing before treating the PDF link as a one-time or time-boxed credential.
</callout>
## 2.4 Webhook HMAC
Call: `authenticate.webhook(request)`.
Verifies the `X-Shopify-Hmac-Sha256` header against the raw request body, using the app's secret key with a constant-time comparison. A missing or invalid signature makes this call throw, which Shopify treats as a failed delivery and retries later. On success it also hands the handler `shop`, `topic`, and the parsed `payload`.
## 2.5 OAuth install / login flow
- `GET /auth/*` runs `authCallbackLoader`, which calls `authenticate.admin(request)`. That call performs the actual OAuth handshake (state validation, token exchange) and saves the resulting session. It throws its own redirect on success, so this loader rarely returns anything itself.
- `GET /auth/login` with no `shop`/`host` param shows a plain, non-embedded "install from the App Store" page. If `shop`/`host` **is** present (a returning merchant whose session expired), it redirects straight to `/auth?<params>` instead of showing the form.
- `POST /auth/login` validates the submitted shop domain via the SDK's `login(request)` and maps errors (`MissingShop`, `InvalidShop`) to form messages.
<callout icon="ℹ️" color="gray_bg">
	`shopify.app.toml` declares three OAuth redirect URLs: `/auth/callback`, `/auth/tokens`, and `/api/auth`. The first two are covered by the `auth.$.jsx` catch-all. No route file matching `/api/auth` exists under `app/routes/` - flagged here as an open question rather than guessed at.
</callout>
## 2.6 CORS
`app/utils/cors.js` exports one helper, applied to `/api/quote`, `/api/config`, `/api/upload`, and `/cart`:
```javascript
function buildCorsHeaders(methods = "GET, OPTIONS") {
  return {
    "Access-Control-Allow-Origin": "*",
    "Access-Control-Allow-Methods": methods,
    "Access-Control-Allow-Headers": "Content-Type",
  };
}
```
The origin policy is fully open (`*`). That's intentional: real protection comes from the App Proxy signature check on each route, not from CORS. Only the `Content-Type` header is allowed through preflight. `/api/reply`, `/api/quote/:id/pdf`, and `/health` don't set these headers at all - they're either same-origin admin calls or direct downloads, not cross-origin fetches.

# 3. Storefront-facing public APIs
Called from the storefront theme extension or a customer's browser. No Shopify admin session is involved in any of these.
## GET / POST /api/quote
Route: `app/routes/api.quote.jsx` -> `app/domain/quotes/storefrontQuote.server.js` -> `app/domain/quotes/quotes.server.js`
**Description:** `GET` returns the theme block's display settings. `POST` submits a new quote request.
**Auth:** App Proxy signature (see 2.2 above).
**Request - GET:** no parameters beyond what App Proxy verifies.
**Request - POST:** JSON body.
```json
{
  "productId": "123456",
  "productTitle": "Widget",
  "variantId": "789",
  "variantTitle": "Blue / Large",
  "customerName": "Jane Doe",
  "customerEmail": "jane@example.com",
  "customerPhone": "+1 5551234567",
  "companyName": "Acme Co",
  "quantity": "3",
  "message": "Need this by Friday",
  "cartItems": [
    { "productId": "123456", "variantId": "789", "productTitle": "Widget", "quantity": 3, "price": "19.99", "offerPrice": "15.00" }
  ],
  "formFields": [{ "label": "Delivery Date", "value": "2026-08-01" }]
}
```
```bash
# Illustrative only - this route only accepts requests forwarded through
# Shopify's App Proxy, so a bare curl call will get a 401.
curl -X POST "https://{shop}.myshopify.com/apps/{subpath}/api/quote" \
  -H "Content-Type: application/json" \
  -d '{"customerName":"Jane Doe","customerEmail":"jane@example.com","productId":"123456"}'
```
Validation rules:
- `customerName` and `customerEmail` (trimmed) are required.
- Every field the shop's Form Builder schema marked `required` must be present in `formFields`, or the request is rejected with the missing field names. This check fails open on unexpected errors (e.g. a corrupt stored schema), so a schema bug can never block submissions.
- There is no spam or rate limiting on this endpoint.
Side effects, all fire-and-forget (a failure here is logged but never changes the response): a sequential quote number is assigned, a merchant-notification email goes out if one is configured, and a buyer-confirmation email goes out with a tokenized PDF link unless auto-response is disabled.
**Response - GET** (`200`):
```json
{
  "isEnabled": true,
  "hideForGuestsOnly": false,
  "buttonText": "Request a Quote",
  "buttonColor": "#1a1a18",
  "buttonTextColor": "#ffffff",
  "showPhone": true,
  "showCompany": true,
  "showQuantity": true,
  "showMessage": true,
  "thankYouMessage": "Thank you! We will be in touch shortly."
}
```
**Response - POST success** (`200`):
```json
{ "success": true, "quoteId": "clx1a2b3c4d5" }
```

## GET /api/export
Route: `app/routes/api.export.jsx` (`csvExportLoader`) -> `app/domain/export/exportQuotes.server.js`
**Description:** downloads quotes as a CSV file. Loader only - there's no `action`, so any non-GET verb gets React Router's default `405`.
**Auth:** Shopify admin session.
**Request:** query parameters `status` (exact match), `from` / `to` (inclusive `createdAt` bounds). No pagination - every matching row is streamed.
```javascript
GET /api/export?status=new&from=2026-07-01&to=2026-07-31
```
**Response:** `200`, `text/csv`, `Content-Disposition: attachment; filename="quotes-<date>.csv"`. Columns: `ID, Status, Customer Name, Email, Phone, Company, Product, Quantity, Message, Quoted Price, Currency, Created, Updated`.
## GET /api/analytics
Route: `app/routes/api.analytics.jsx` -> `app/domain/analytics/analytics.server.js`
**Description:** dashboard metrics for the current shop. Loader only.
**Auth:** Shopify admin session. No parameters - scoped to `session.shop`.
**Response** (`200`, `Cache-Control: private, max-age=60`):
```json
{
  "total": 128,
  "thisMonth": 24,
  "newCount": 5,
  "replied": 40,
  "responseRate": 31,

```
`dailyTrend` is always exactly 30 entries, zero-filled for days with no activity. `responseRate` is `round(replied / total * 100)`.

Calls `authenticate.admin(request)` purely to gate the route, then returns `{ "apiKey": "...", "buttonColor": "..." }` used to configure the embedded app shell and Polaris button colors. No `action`.

# 5. Auth / OAuth routes
## GET /auth/*
Route: `app/routes/auth.$.jsx` -> `app/domain/auth/auth.server.js` (`authCallbackLoader`, `authHeaders`)
The OAuth catch-all, under `authPathPrefix: "/auth"`. Calls `authenticate.admin(request)`, which runs the handshake/token exchange and saves the session, throwing its own redirect on success. The `headers` export sets the CSP `frame-ancestors` headers required to render inside the Shopify Admin iframe.
## GET / POST /auth/login
Route: `app/routes/auth.login/route.jsx` -> `app/domain/auth/auth.server.js` (`loginLoader`, `loginAction`)
**GET** - with no `shop`/`host`, shows a plain "install from the App Store" page. With `shop`/`host` present, redirects immediately to `/auth?<params>` instead.
**POST** - validates the submitted shop domain and maps errors to form messages.

# 6. Webhook endpoints
All five share the same verification:
```javascript
const { shop, payload, session } = await authenticate.webhook(request);
```
This checks the `X-Shopify-Hmac-Sha256` header against the raw body. A missing or invalid signature throws, and Shopify retries delivery. Every route file below is a one-line re-export - all the logic lives in the matching `app/domain/webhooks/*.server.js` file.
## POST /webhooks/app/scopes_update
File: `app/domain/webhooks/appScopesUpdate.server.js`
Fires when a merchant approves a changed scope grant. Updates the stored session's `scope` column from `payload.current`. Returns `200` with an empty body.
<callout icon="⚠️" color="yellow_bg">
	This is the only one of the five webhooks with no try/catch around its database write - an unhandled error here produces a non-200 response and triggers a Shopify retry, unlike the other four.
</callout>
## POST /webhooks/app/uninstalled
File: `app/domain/webhooks/appUninstalled.server.js`
Fires immediately on uninstall. Deliberately does **not** delete business data - it only deletes session rows for the shop. That gives a roughly 48-hour grace period (until `shop/redact` fires) during which a reinstall recovers all merchant data intact. Always returns `200`.
## POST /webhooks/customers/data_request (GDPR - right of access)
File: `app/domain/webhooks/customersDataRequest.server.js`
Fires when a customer asks for a copy of their data. Looks up all quotes for `payload.customer.email`. If any exist and a merchant notification address is configured, it emails the merchant (not the customer) a data-access report - the merchant is the GDPR data controller and relays the data onward. Always returns `200` with an empty body; per Shopify's own guidance, only acknowledgement of receipt is required.
## POST /webhooks/customers/redact (GDPR - right to erasure)
File: `app/domain/webhooks/customersRedact.server.js`
Anonymizes rather than hard-deletes matching quotes: name, email, phone, company, message, and all free-text/history fields are cleared or set to "[redacted]". Operational fields (status, quantity, product, quote number, timestamps) are left intact so historical analytics aren't skewed. Always returns `200`.
## POST /webhooks/shop/redact (GDPR - full shop purge)
File: `app/domain/webhooks/shopRedact.server.js`
Fires roughly 48 hours after uninstall, on Shopify's own schedule. Checks for an active session first - if one exists (the merchant reinstalled), deletion is skipped entirely. Otherwise it purges every shop-scoped table (quotes, targeting rules, price-hiding rules, config, email templates, form schema, general settings, sessions) using `Promise.allSettled`, so one failing table doesn't block the rest. Always returns `200`.

# 8. Known caveats
<callout icon="⚠️" color="yellow_bg">
	Flagged during this documentation pass - worth a look before relying on the affected behavior.
	- **API version mismatch:** the Admin API client uses "2025-10"; `shopify.app.toml` declares "2026-07" for webhook payloads.
	- **PDF download tokens never expire** (see 2.3) - a deterministic HMAC with no timestamp or nonce.
	- **`/api/auth`** is a declared OAuth redirect URL in `shopify.app.toml`, but no matching route file exists under `app/routes/`.
	- **`registerWebhooks`** is exported from `shopify.server.js`, but no call site was found in the auth/webhook code - webhook subscriptions appear to be managed entirely through `shopify.app.toml` + `shopify app deploy`.
</callout>
